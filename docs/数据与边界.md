# 数据与边界

这份文件定义两件事：表要长什么样，什么东西不进仓库。

## 一 点位表 `points.csv`

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 点位编号，`P-01` 这类短码。用来和记录表关联，不用中文名当主键。 |
| `name` | 是 | 显示名。真实名字在本地库，进仓库时一律换成占位符。 |
| `type` | 否 | 类型标签，自己定（门店、社区、商圈、园区……）。图上用来区分形状。 |
| `lng` `lat` | 是 | 经纬度，十进制。**同一份表里只能有一种坐标系**，混用会偏几百米。 |
| `owner` | 否 | 负责这个点位的组员。 |
| `status` | 是 | 只用四个词：`未接触` `已接触` `有进展` `重点跟进`。多一个词，筛选和配色就要重做。 |
| `last_visit` | 否 | 最近一次到访日期，`YYYY-MM-DD`。 |
| `visits` | 否 | 累计到访次数，整数。 |

状态词表为什么只有四个：多了记不住，记不住就填错。少了分不出优先级。这四个词对应「还没去 / 去过了 / 去过且推进了 / 需要盯着」，够用。

## 二 记录表 `notes.json`

一条记录 = 一次到访。

```json
{
  "date": "2026-06-12",
  "point_id": "P-02",
  "owner": "组员A",
  "reached": 4,
  "leads": 2,
  "deals": 0,
  "intent": "中",
  "next_step": "周六上午再约",
  "raw": "原始口述文本，保留不改"
}
```

- `reached`：当场接触的人数（不是预估）。
- `leads`：留下可联系方式的数。
- `deals`：当场或已确认的成交数。跟单周期长的业务，这一天填 0 是正常的。
- `intent`：`高` `中` `低`，三档。不做五分制，没人能稳定区分五个档。
- `raw` 必须保留。它是唯一能和人对账的东西，结构化字段错了，回到原文能查。

## 三 坐标系

只用一种。国内底图常见 GCJ-02，GPS 原始是 WGS-84，两者差几百米。混在一张图上的结果，是点位看着在马路对面，实际隔了一条街。

取数的时候记下来源，落库时统一转成一种，之后不再动。

## 四 什么不进仓库

- **点位数据本身**：不进。点位是各地方言，换城市就失效，传上去既没用又露作业面。
- **客户信息**：不进，也不进示例。姓名、电话、微信、诉求一律不出本机。
- **密钥**：不进，进环境变量或你自己的本地配置。
- **具体的数据获取实现**：不进。这份仓库只给字段契约和处理逻辑，取数由你按自己所在的平台和行业接，`scripts/` 里留了接口位置，没有写死任何一家的调用方式。

## 五 一条底线

示例里的每一条记录都必须是虚构的。真实数据哪怕只有三条，也不要为了"示例更真实"放进仓库。仓库一旦公开，历史提交删不干净。
